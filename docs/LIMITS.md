# reactc: known limits

What reactc does not do yet, kept current as the compiler grows. Details are in the
[compiler README](../compiler/README.md).

## What works end to end today

- **Template:** projects generated by `reactc new` (TypeScript API, React
  client, shared types) build both executables from one `reactc.config.json`.
- **Servers:** `fetch` with all methods and headers, the Node API probe
  (31/31), `worker_threads`/`fork` as native threads, and `@reactc/threads`
  (shared heap, async `run()`, threads as promises).

## Platforms and toolchain

- **Hosts.** Windows (x64) and Linux (x86-64). Windows builds run the bundled C
  toolchain (`tools/local`, an Ubuntu 26.04 sysroot with GCC 15 and MinGW-w64)
  through WSL. That WSL distribution needs a glibc at least as new as the
  sysroot's, so use Ubuntu 26.04. The executables reactc produces do not need
  WSL.
- **Linux runtime.** Linux executables that use Node APIs link libuv as a
  shared library: install `libuv1t64` (Ubuntu) on the machine that runs them.
- **Targets.** Not covered: macOS, ARM64, Android, and the WASI target's Node
  APIs beyond `fs`/`stream`.
- **Compile times** can be long. An Express server's C takes about 25 minutes
  in one optimising compiler pass.

## HTTP client (`fetch`)

Native builds negotiate HTTP/2 over HTTPS using ALPN and fall back to
HTTP/1.1. Use `fetch(url, { httpVersion: '2' })` for a cleartext HTTP/2 origin
with prior knowledge. HTTP/2 requests share a connection per origin and TLS
options. The HTTP/2 client disables server push. Both protocols support
streaming uploads (`duplex: 'half'`), redirects, cancellation and incremental
gzip, deflate and Brotli decoding. `Request` and `Response` expose readable web
streams, cloning, and `blob()` and `formData()` readers.

- No HTTP/3, proxies or Node-compatible custom dispatchers. `Blob` and
  multipart request bodies are assembled in memory before transmission.
- Incremental decoding can queue decoded output ahead of a slow reader.
- The cookie jar is in memory only (no persistence, no public-suffix list,
  `SameSite` ignored); `clearCookies()` from `reactc:fetch-tcp` empties it.
- Native UI builds with `--http-origin` accept relative URLs and restrict
  requests and redirects to the configured origin.
- WASI builds still use the host HTTP transport with `--http-origin`. That
  transport is limited to 64 KiB of UTF-8 and has no cookies, redirects or
  streaming.

## npm packages and JavaScript

- Node packages with native addons (`sqlite3`, `bcrypt`, `sharp` and similar)
  cannot be compiled as they are. Their underlying C libraries can be called
  directly with [`@reactc/native`](../packages/reactc-native/README.md).
- Porffor has no `eval`/`new Function`, and dynamic `require` with computed
  paths fails.
- Worker and fork entries must be literal paths (`./file.js`).

## Node APIs

- Covered: `fs`, `fs/promises`, `stream`, `net`, `dgram` (UDP, in servers and
  UI apps), `child_process`, `zlib`, `crypto` (including WebCrypto and
  scrypt), `http`, `https`, `path`, `url`, `worker_threads`.
- `dgram` sends to numeric addresses and `localhost`, not other host names.
- Not covered: `fs.watch`, links and `lstat` on Windows, ownership changes,
  most of `http2`.
- `fork()` children are threads in the same process. They share `pid`, the
  environment and the working directory, and `kill()` cannot interrupt a busy
  thread.

## Threads

- **`worker_threads`/`fork`.** Messages are structured clones. There is no
  `SharedArrayBuffer`, no `MessageChannel`, and transfer copies rather than
  moves. Workers cannot start workers, and a worker cannot link the uWS HTTP
  server.
- **`@reactc/threads`.**
  - At most 63 threads running or not yet joined at once (joined threads' slots
    are reused), x86-64 only (TSO ordering is
    assumed).
  - One global structure lock and 256 striped monitors, so heavy property
    adding or pushing from many threads serialises.
  - Safepoints are at loop heads, allocation and event-loop waits. Deep
    recursion without loops or allocation delays a collection.
  - It cannot be combined with `worker_threads`/`fork` in one program.
  - Awaiting a thread polls its state about every millisecond (one timer
    tick, about 15.6 ms on Windows).
  - It rewrites Porffor alpha-22's C text, and fails loudly if Porffor's
    output changes.

## Native libraries (`@reactc/native`)

- **Platform.** x86-64 only; not available for the WebAssembly target.
- **Call shape.** At most 32 arguments per call. Linux variadic calls take at
  most 6 integer and 8 floating arguments.
- **Structs by value.** Struct arguments and returns by value are not
  supported (pass pointers).
- **Callbacks.** At most 64 live callbacks, called on the JavaScript thread.
- **Copies.** Buffers and strings are copied for each call.

## React UI (native renderer, not a browser)

- **Layout and styling.**
  - Borders are painted inside the box and do not push the content in.
  - Absolutely positioned children inside CSS-styled boxes stay in the
    normal flow.
  - Not supported: `:active`, `:focus-visible`, `box-shadow`, `transform`,
    `transition`, `outline`, `resize`, `word-break` and scrollbar styling.
- **Keyboard.**
  - Plain typing in a text field is not reported to `onKeyDown`, and there is
    no `keyup`/`keypress`.
  - Escape does not leave a field, and undo is one level.
  - There is no arrow-key navigation in selects or radio groups.
  - Tab does not scroll focus into view inside nested scroll areas.
  - IME and screen readers are untested or absent.
- **Not implemented.** Routing, Tailwind translation and most browser-API
  bindings.
- **Component libraries.** Ones that rely on unsupported CSS (MUI and similar)
  will look off or fail to compile.
- **Dialogs.** File dialogs are unavailable in the generic Windows host.
